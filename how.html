the loop

One model. One workflow. Four moves, repeated until day 100 beats day 1.

MARS takes an open-weights model and points it at the tasks your team actually runs. It observes what happens, evaluates every output against checks you write as code, refines the weights on what passed, and ascends only when the new weights beat the old ones. Then it goes again.

What it is not: a benchmark, a chat wrapper, or a place your data goes. Traces, evals and weights stay on hardware you own.

iter 001 · observe

Start from real traces, not a demo set.

A trace is one run of your workflow: the input, every tool call, the model's output and what happened next. MARS captures them from where the work already happens, through a drop-in SDK or a local proxy, and keeps them on your machine.

No labelling sprint. The first hundred traces are the model's first look at the mission.

iter 002 · evaluate

Evals are code you write once and run on every output.

Each trace is scored by small, deterministic checks: did the output have the right shape, did it match the reference, did it finish within budget. Pass or fail, per trace, every time.

// evals/triage.ts
export default eval('triage', ({ out, ref, ms }) =>
  out.label === ref.label &&
  out.owner in ref.team &&
  ms < 800,
)

The pass set is the only thing the next move is allowed to learn from.

iter 003 · refine

Fine-tune on what passed, on hardware you own.

MARS trains a low-rank adapter on the pass set: hours on a single 24 GB GPU, not days on a cluster. Nothing the model gets wrong is rewarded; nothing leaves the box.

The result is a candidate, not a release. It still has to win.

iter 004 · ascend

New weights ship only if they beat the old ones.

Candidate and incumbent run the same held-out evals. If the candidate wins, it becomes the model; if not, it is discarded and the incumbent keeps flying. Either way the loop starts again with fresh traces.

Every mission starts with one task.
